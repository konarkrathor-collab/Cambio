# Build Plan & Acceptance Gates

This is the working plan for turning the benchmark-proven design into a running application. It is the authority on **stack, repository layout, stage order and what "done" means**. Where it conflicts with an earlier document (02, 04, 06, 07), this one wins — those documents carry a pointer back here.

Work is done one **stage** at a time. A stage is finished only when its acceptance gate passes under independent verification (§4), not when the implementer says it is.

---

## 1. Stack (confirmed with the course faculty)

| Tier | Language | Responsibility |
| :--- | :--- | :--- |
| **Backend** | **Java 17** (plain `javac`, no Gradle/Maven) | *All computation*: matching, order book, arbitrage scan, accounts, ticker search, compression, API server |
| **Data feed** | **Python 3** | *Data acquisition only*: fetch rates from Finnhub / Frankfurter and forward them to the backend. No business logic. |
| **Dashboard** | **React** (Vite, JavaScript) | Visualisation and order entry |

Consequences worth stating once:

- The Python feed never derives cross-rates, builds the graph, or decides staleness. It parses and forwards. Everything computed lives in Java.
- The backend uses only the JDK: `com.sun.net.httpserver` for REST, **Server-Sent Events (SSE)** for pushing updates to the browser (replaces the WebSocket server in doc 02), a small hand-written JSON reader/writer, flat-file persistence.
- Machine baseline: Java 17, Python 3.13 (`websocket-client` installed), Node 26 / npm 11.

### 3a. Decision — the price ladder

After Runs 12–14 (`benchmark/results/RESULTS.md`), the Radix Tree no longer has a measured advantage over the alternatives:

| Candidate | Speed (walk) | Tick-range robust | Resident memory | Code / risk |
| :--- | :--- | :--- | :--- | :--- |
| **Radix Tree** (16-ary) | tie with Red-Black | yes | ~52–59 B/level — **9–22% more than Red-Black, ~2× B+ tree** | 236 lines, no restructuring, fixed depth |
| **B+ tree** (order 32) | ties or beats radix (~9% ahead) | yes | **~29 B/level (leanest)**, ~7× less allocation churn | 306 lines, split/borrow/merge paths |
| **Red-Black tree** | tie with radix | yes | 48 B/level | simplest balanced tree |

Radix's remaining case is *zero restructuring and less code*. The B+ tree is already implemented and oracle-validated in `benchmark/`, which lowers its porting risk; Stage 0's parity gate would catch any slip.

**Decision: the price ladder is the B+ tree (order 32).** The evidence favours it on every axis the lab measured, and "we benchmarked our own first pick and replaced it" is a strong account for the viva. It remains reversible, and to keep it so:

- The engine depends only on a `PriceLadder` interface (best-bid/ask, insert level, remove level, walk K levels; each leaf holds a `PriceLevel`), never on the B+ tree class directly, so Radix or Red-Black can be dropped in later without touching the matching loop.
- Stage 0 ports all six structures, the ladder being the B+ tree, and it must pass the same walk, wide-range and sorted parity workloads as the benchmark version.
- The team can still reverse this at the sync on new benchmark evidence (§3 rule 11).

## 4. Supervision protocol

1. The implementer works on **one stage**, then stops and posts a report: what was built, the exact commands run with their output, any deviation from this plan, any bug found.
2. The supervisor verifies independently: fresh build, run the tests, run the demo/endpoints, read the diff for rule violations (§3: `java.util` in structures, `double` in matching, secrets, attribution lines, history rewrites).
3. Only after an explicit **ACCEPTED** does the next stage start. A failed gate means fix and re-report, not move on.

## 5. Stages

### Stage 0 — Port the structures into the backend

**Build.** Production versions of the six structures under `backend/src/ads/…`, ported from `benchmark/src/ads/bench/…`. Changes from the benchmark versions are limited to what production needs:
- The price ladder (the B+ tree, §3a) stores a **`PriceLevel`** at each leaf (price tick, total volume, an order queue head/tail) instead of just a volume — the matching engine needs the queue at the level. Bids and asks each get their own ladder (best-ask = min, best-bid = max).
- The order queue becomes: a doubly linked list per `PriceLevel` plus **one global order index** (own hash table, `orderId → Order node`, chaining, resize at load 0.75) so cancel is O(1) and can reach the right level via the node's level pointer.
- Bellman-Ford keeps `CycleTrace`; cache keeps hash + LRU; trie keeps the child bitmap; Huffman keeps its byte-exact codec.
- Strip benchmark-only scaffolding (timing hooks, `dump` helpers used only by oracles).

**Tests.** `backend/test.sh` runs a plain-Java test runner (no JUnit). For each structure, a thin adapter implements the matching `benchmark` interface (`LadderOps`, `QueueOps`, `CacheOps`, `TickerOps`, `GraphOps`, `CompressorOps`) by delegating to the production class, then runs the benchmark's **own** correctness gate against its oracle on the same seeded workloads (compile tests with `benchmark/out` on the classpath; run `benchmark/build.sh` first). Parity with the benchmark's checksums is therefore literal, not re-implemented.

**Gate.**
- `backend/build.sh` clean; `backend/test.sh` all green.
- All six parity checks pass, the ladder under the walk, wide-range and sorted workloads.
- A grep proves no `java.util` import in any production structure class.
- The report lists production-vs-benchmark timing for each structure (informational; a regression above 25% must be explained).

### Stage 1 — Matching engine, services, command-line demo

**Build.**
- `Order`, `PriceLevel`, `OrderBook` (one per pair: bid ladder + ask ladder), **one engine-wide `OrderIndex`** (order ids are global and `DELETE /api/orders/{id}` carries no pair, so cancel must find the order from the id alone; each order records its pair and side so an emptied level is removed from the right ladder), `MatchingEngine`, `Trade`. Per-pair book lookup is on the hot path, so key it by a small integer pair id from the Directory trie into an array, not a `java.util` map. All changes to an order's `remaining` must go through one `PriceLevel` method that also updates the level's volume, so the volume invariant cannot drift. Rules are fixed in **Appendix A**; do not improvise them.
- **Scanner:** rate store, graph construction (edge `u→v` weight `-ln(rate)`), cross-rates derived through USD in Java, Bellman-Ford scan, minimum-profit threshold (default 0.001%) so floating-point noise is never reported as arbitrage, result = cycle + multiplier + profit %.
- **Directory:** Trie seeded with the 12-currency, 132-pair universe used in the ticker benchmark; `contains`, `prefixSearch`.
- **Vault:** hash + LRU account cache backed by a flat file (`backend/data/accounts.jsonl`, written atomically); accounts survive a restart.
- **Logbook:** completed trades buffered, rotated into a Huffman-compressed archive file; archive decodes back to byte-identical records.
- `backend/run.sh demo`: matches 1,000 seeded orders and prints trades, then loads an artificial triangular arbitrage and prints the detected cycle with multiplier.

**Tests.** A **reference matcher** in the test tree (may use `TreeMap` + `ArrayDeque`) implements Appendix A the obvious way. Differential test: a seeded stream of ≥100,000 limit/market/cancel orders in a narrow price band (so orders cross constantly) is fed to both matchers; the full trade lists and the final book depth must be **identical**. Plus hand-written scenario tests: partial fill, FIFO within a level, price improvement (trade at resting price), market sweep across levels, cancel of a resting order, cancel of an unknown/filled order, rejection cases.

**Gate.** Build and tests green; differential test identical over at least three seeds; demo output reproducible; restart test shows accounts persisted; logbook round-trip byte-identical; same grep rules as Stage 0 for the engine hot path (no `java.util`, no `double`).

### Stage 2 — Python data feed

**Build.** `feed/feed.py` (+ `requirements.txt` with `websocket-client` only; HTTP via `urllib`).
- **First task:** call Finnhub `GET /forex/symbol?exchange=oanda` once (key from environment) and record in `feed/symbols.json` which OANDA pairs exist for the 8-currency roster (USD, EUR, GBP, JPY, AUD, CAD, CHF, INR) and which cross-pairs are *not* directly streamed. This closes the open item in doc 06 §4.
- Connect to `wss://ws.finnhub.io?token=…`, subscribe to the symbols, batch ticks (≤ 250 ms) and forward them to the backend (payloads in **Appendix B**).
- Reconnect with backoff 1, 2, 4, 8, 10 s (cap) and re-subscribe after every reconnect. If disconnected > 15 s, forward an hourly Frankfurter snapshot (`source: "frankfurter-fallback"`) until the socket returns.
- Malformed messages are logged and skipped; the process never crashes on bad input. Missing `FINNHUB_API_KEY` exits immediately with a clear message.
- Modes: `--capture FILE` (record raw ticks as JSON lines) and `--replay FILE` (forward a recorded log; lets the system be demoed and tested with no network and no key). Commit one real capture (a few minutes of ticks, under 2 MB, containing no key) as `feed/samples/finnhub_ticks_<date>.jsonl` so a fresh clone can replay it.
- **The forex market is closed at weekends** (roughly Friday evening to Sunday evening UTC). Zero ticks then is expected, not a bug: treat Finnhub's `{"type":"ping"}` messages as keep-alives, report "connected, no ticks" in the status, and if no live ticks are available when you capture, say so in the report instead of fabricating a sample. The user will run the live check during market hours.
- Java side: a minimal server skeleton in `ads.api` (`com.sun.net.httpserver`, a small hand-written JSON reader/writer in `ads.util`) with just two endpoints for now: `POST /api/market/rates` (updates the scanner's rate store, triggers a throttled scan, `SCAN_THROTTLE_MS = 500`) and `GET /api/market/rates/status` (source, last tick time, stale symbols, tick count, scan count, whether the last scan found a cycle). Stage 3 grows this same server into the full gateway, so design it to be extended. All engine access goes through one thread.

**Gate.** With the backend running, `feed.py --replay` drives `GET /api/market/rates/status` to show ticks received and the scanner running; a live run with the real key (run by the user) shows `source: "finnhub-ws"`; unplugging the network flips to `frankfurter-fallback` within ~15 s and back on reconnect; garbage input does not crash either process.

### Stage 2 addendum — four corrections found in review (do these first, as their own commit, before any Stage 3 work)

1. **Stale quotes must not reach the scan.** Staleness is currently only *reported*. The scanner must ignore any direct quote older than `STALE_AFTER_MS` (30 s) and any cross-rate that depends on one, so that a feed that stops makes arbitrage alerts stop instead of freezing them. The scan result and the status report how many edges were excluded. Rates from a fallback snapshot share the snapshot's receive time and stay valid for 2 hours (twice the hourly poll). When the source switches (live to fallback or back), clear the rate store so snapshot and live rates are never mixed in one graph. Tests: advance a fake clock past 30 s and assert the scan loses the stale edges; assert no alert survives a dead feed; assert no cycle can mix the two sources.
2. **INR is fallback-only.** OANDA streams no INR pair (all 7 are missing, see `feed/symbols.json`), so in live mode the scanner's graph has 7 currencies and 21 pairs; INR appears only while the fallback snapshot is the source. Update doc 06 §4 to say so. Order trading still supports INR pairs through the Directory.
3. **Data-driven profit threshold.** Real ticks alternate between bid and ask, so the 0.001% default reports "arbitrage" on the real capture (for example +0.0056%). Using only the committed capture in `feed/samples/`, replay it through the scanner offline and report, for thresholds 0.001, 0.005, 0.01, 0.02 and 0.05%, the share of scans that report a cycle, plus the p50, p90, p99 and max best-cycle profit. Make the threshold configurable (`serve --min-profit PERCENT`, or the `MIN_PROFIT_PERCENT` environment variable) and default it to the smallest value for which fewer than 1% of scans of the real capture report a cycle. The demo's injected +0.4% must still be detected. Record the table in `backend/BUGS.md` and doc 06.
4. **Portability.** `feed/replay_check.sh` uses GNU `timeout`, which macOS does not have. Replace it with something portable (for example `curl --max-time`) and check every script in the repo for other GNU-only commands. The demo machine is a Mac.

### Stage 3 — API gateway and frozen contract

**Build.** The Java HTTP server (`com.sun.net.httpserver`) with one engine thread serialising all mutations. Endpoints:

| Method & path | Purpose |
| :--- | :--- |
| `POST /api/orders` | Submit limit/market order (shape per doc 02 §4; adds `REJECTED` with a reason) |
| `DELETE /api/orders/{id}` | Cancel a resting order |
| `GET /api/orderbook/{pair}?depth=N` | Bid/ask ladder snapshot with cumulative volume |
| `GET /api/arbitrage/scan` | Latest scan result |
| `GET /api/arbitrage/graph` | Nodes, edges, rates and the current cycle (for the visual) |
| `POST /api/market/rates` | Ingestion from the feed (Appendix B) |
| `GET /api/market/rates/status` | Source, last tick time, stale symbols (doc 06 §7) |
| `GET /api/tickers?prefix=US` | Directory search |
| `GET /api/accounts/{traderId}` | Balance and margin. `traderId` is a number (the engine uses `long`); doc 02's `"T101"` was illustrative, and the dashboard may display it as `T101` |
| `GET /api/accounts` | List accounts |
| `POST /api/accounts` | Create an account `{traderId, cash, marginLimit}`; 409 if it exists |
| `POST /api/simulate` | Stage 4 |
| `GET /api/inspector/{pair}` | Internal structure state: levels, queue lengths, ladder node shape (for the under-the-hood view) |
| `GET /api/stream` | **SSE**: `BOOK_UPDATE`, `TRADE`, `LOOPHOLE_ALERT`, `RATE_TICK` |
| `GET /api/health` | Liveness |

Errors use one shape: `{"error":{"code":"…","message":"…"}}` with correct HTTP codes (400 bad input, 404 unknown id, 409 conflict). CORS allows the Vite dev origin. Pair strings are case-sensitive in the Directory (the Stage 0 trie rejects characters outside `A–Z` and `/`), so handlers **upper-case pair input at the API boundary** before any lookup. The builder writes **`documentation/09_api_contract.md`** with every endpoint, request/response example and error code.

**Stage 3 decisions (fixed here so the contract does not drift):**
- **Composition.** One `ads.api.App` wires the Directory, Vault (`--data-dir`, default `backend/data`), MatchingEngine, Logbook, ArbitrageScanner and MarketService onto the existing `ApiServer` and `EngineThread`. Every command goes through the engine thread; handlers never touch engine state directly. After each command the engine thread calls `logbook.rotateIfDue()`. On shutdown, flush the Vault and write the final Logbook segment.
- **Prices and pairs at the boundary.** The API speaks decimals and `EUR/USD`; the engine speaks integer ticks and pair ids. Convert with exact decimal parsing (`BigDecimal` is fine in the `api` layer). A price that is not an exact multiple of the pair's tick size is a business rejection `BAD_PRICE`. Never convert a price through `double`. Pair names in a URL path use a hyphen (`/api/orderbook/EUR-USD`); bodies use `EUR/USD`; both are upper-cased. Expose each pair's `tickSize` in `/api/tickers`.
- **Two kinds of failure.** A malformed request (bad JSON, wrong types, a missing field, an unknown enum value) is HTTP 400 with the error shape. A well-formed order the engine refuses is HTTP 200 with `{"status":"REJECTED","reason":"…"}`. An unknown order id on cancel is 404; creating an account that already exists is 409.
- **Order ids** are shown as `ORD-<n>` and accepted as `ORD-<n>` or `<n>`.
- **Accounts.** If the accounts file is empty at startup and `--seed-demo-accounts` is given, create the 12 demo traders the demo uses.
- **Order book snapshot** `GET /api/orderbook/{pair}?depth=N` (default 10, maximum 50): `bids` and `asks`, each level `{price, volume, orders, cumulative}`, both sides best-first, plus `seq` and `lastTradePrice` (or null).
- **SSE** `GET /api/stream`: events `BOOK_UPDATE` (the touched pair's top-10 snapshot after every order or cancel that changed it), `TRADE`, `LOOPHOLE_ALERT` (when a scan newly finds or loses a cycle, not on every scan) and `RATE_TICK` (at most 4 per second per pair). Send `retry:` and `id:` fields and a comment heartbeat every 15 s. A slow or dead client must never block the engine thread: give each client a bounded queue and drop the client when it overflows.
- **Inspector** `GET /api/inspector/{pair}`: for each side, the levels with order counts and queue heads, plus the ladder's shape (height, node and leaf counts). Add the read-only `describe` method this needs to `BPlusTreeLadder`.
- **Graph** `GET /api/arbitrage/graph`: `nodes` (currencies), `edges` (from, to, rate, stale) and the current `cycle` (or null).
- **Network.** Bind to 127.0.0.1 by default (`--host`, `--port`). CORS allows `http://localhost:5173` and `http://127.0.0.1:5173` only.
- **Scripts** (`smoke.sh` and any other) must run on macOS and Linux: `curl` only, no GNU-only commands.
- **Tests** add HTTP-level tests with `java.net.http.HttpClient`: a crossing pair of orders produces trades and updated balances; cancel; every error path (400, 404, 409, and REJECTED with each reason); price conversion (exact, a non-multiple of the tick, absurdly large); upper-casing and hyphenated paths; an SSE client receives BOOK_UPDATE, TRADE and LOOPHOLE_ALERT in order; a deliberately slow SSE client does not stall order flow; 200 concurrent orders from 8 threads give the same result as a serial replay; accounts and the logbook survive a restart through the API.

**Gate.** `backend/scripts/smoke.sh` exercises every endpoint with `curl`; the SSE stream shows events while orders are placed; malformed JSON returns 400 and the server keeps running; the whole backend and feed suites still pass; `09_api_contract.md` documents every endpoint using real requests and responses captured from the running server. The supervisor reviews and **freezes** the contract — Stage 5 may not start before this.

### Stage 3 addendum — three follow-ups found in review (do these first, as their own commit, before any Stage 4 work)

1. **Exact triangular detection (closes B8).** The scanner's shifted Bellman-Ford passes miss most real cycles near the threshold (13% of scans reported a cycle at 0.01% where an exhaustive search finds one in 66%). This project is *triangular* arbitrage, and an exact check over every ordered triple of currencies is cheap (V = 12 gives 1,320 triples, V = 20 gives 6,840). Add it to the scanner: report the most profitable of the Bellman-Ford result and the best triangle that is at or above the threshold. Tests: for random rate sets the scanner must report a cycle whenever *any* triangle reaches the threshold (compare with brute force over all triples, no gap allowed); every previous scanner test still passes; the demo's +0.4% is still found. Re-run `threshold-study`, add a "triangles only" column, and report the new table and the scan time at V = 12 and V = 20 (no-arbitrage and arbitrage cases).
2. **Ids unique across restarts.** Order ids, trade ids and `seq` restart at 1 on every server start, so the Logbook archive can hold repeated ids and a browser tab can confuse an old `ORD-5` with a new one. Persist the three counters in the data directory together with the Vault's atomic flush, and restore them at startup. Resting orders still do not persist, so cancelling an order from a previous session stays a 404. Update §5 of `09_api_contract.md` in the same commit (this is a compatible change).
3. **Recent trades endpoint (additive).** The dashboard needs trade history on page load, and the event stream only delivers new trades. Add `GET /api/trades?pair=P&limit=N` (`pair` optional, `limit` default 50, maximum 500), returning the most recent trades first from an in-memory ring of the last 500 trades kept on the engine thread, each in the same shape as `trades[]` in §3.1. Add it to the contract with a captured example, to `smoke.sh`, and to the tests.

### Stage 4 — Simulator and load test

**Build.** `POST /api/simulate` runs a seeded order generator *inside the JVM* on an **isolated** engine (its own Directory, Vault and books, no Logbook, no event stream), so a simulation never touches the live books, accounts or the SSE stream. It runs on its own worker thread, not the live engine thread, one at a time (409 `SIMULATION_RUNNING` otherwise), and the request returns when it finishes.

- **Request** (every field optional, out-of-range is 400): `numOrders` (1 to 1,000,000, default 5,000), `seed` (default 42), `baseline` (default true), `scanEvery` (default 100: one scan on synthetic rates after every that many orders; 0 disables), `rateVolatility` (percent per step, 0 to 1, default 0.01).
- **Order mix** (document it in the generator's class comment): seeded, in a narrow price band so orders constantly cross; roughly 55% limit, 15% market, 20% cancels of live orders and the rest invalid inputs so the reject paths run too; 12 simulation traders with generous margin.
- **Response:** `numOrders`, `seed`, `durationMs`, `ordersPerSec`, `trades` (the matches executed), `rejects`, `cancels`, `latencyUs` for `submit` and for `cancel` each `{count, p50, p90, p99, max}` measured per operation *inside* the engine (no HTTP in the number), `scans` `{count, p50Us, p99Us, loopholesFound}`, `tradeChecksum` (FNV-64 over every trade), and, when `baseline` is true, a `baseline` object with the same fields measured on a naive matcher fed the identical stream, plus `checksumMatch` (must be true) and `speedup` (engine ordersPerSec divided by baseline ordersPerSec).
- **The naive baseline** keeps resting orders in a plain array and scans it for the best opposite price on every order, which is the "linear scan" stand-in for doc 04 Phase 5. It is correctness-checked against the engine (same trades), not just timed.
- `GET /api/simulate/last` returns the most recent result (404 if none yet) so the dashboard can show it after a reload. Both endpoints and every field go into `09_api_contract.md` in the same commit (additive), with captured examples.
- `backend/scripts/simulate.sh` (curl only, macOS and Linux) runs a simulation against a server and prints engine versus baseline as a table.



**Gate.** The supervisor re-runs 5,000 and 1,000,000 orders and reproduces the figures within normal variance. Tests: the same seed gives the same `tradeChecksum`; engine and naive baseline agree (`checksumMatch`) over several seeds and sizes; a simulation leaves the live book, accounts and event stream untouched; a second simulation while one runs gets 409; bad parameters get 400; the percentile calculation is checked on a known array. Targets from doc 04 (≥ 50,000 orders/s; scan < 100 µs on a 20-currency graph, taken from `test.sh --scan-timing`) are checked and the **measured** values reported honestly, met or not.

### Stage 4 addendum — four follow-ups found in review (own commit, before Stage 5 work)

1. **A second, deep-book profile for the simulator (additive).** On the default mix the books stay shallow (about 50 resting orders across six pairs), and there a linear scan is as fast as the engine (B11, reproduced independently: 0.5x to 1.04x). That is an honest result and stays the default. The structures matter when books are deep, as real ones are, so add an optional request field `profile`: `"shallow"` (default, today's mix, unchanged byte for byte) or `"deep"`. `deep`: a wide price band (about ±5,000 ticks around the mid), BUYs priced below and SELLs above the mid so most orders rest, roughly 10% aggressive orders that cross, about 10% cancels and a few market orders, so each pair accumulates thousands of resting orders over a long run. Document the mix in `OrderGenerator`. Because the naive baseline costs O(resting orders) per operation, cap `numOrders` at 200,000 when `profile` is `deep` and `baseline` is true (400 otherwise, stated in the contract). Add the field, the cap and captured examples to `09_api_contract.md`, extend `simulate.sh` (`PROFILE=deep`), add tests (deep is deterministic, engine and baseline agree, the deep run really does reach thousands of resting orders), and report both profiles at several sizes. **Report the result whichever way it falls; do not tune the mix to favour the engine.**
2. **A crash test that can fail.** The current test waits for a periodic counter flush and then copies the data directory, so no ids were issued *after* the last flush, which is the one case the 1,000,000 reserve exists for (a mutation removing the reserve passed all 190 tests). Make the flush interval an `App` parameter; in the test set it very long, issue orders, copy the directory (the crash), restart, and assert every new id exceeds every id issued before. Show in your report that removing the reserve now fails the test.
3. **Compare balances, not just trades, between engine and baseline.** A mutation that made the baseline settle at the wrong price passed every test, because only trades, rejects, cancels and resting counts were compared. Include every simulation trader's final cash (and the total) in the engine-versus-baseline comparison, so `checksumMatch` is false if settlement differs. Show that the same mutation now fails a test.
4. **Decision recorded on B8.** Triangular arbitrage is the project's definition and is now exact. The longer (5 to 7 leg) loops that remain unreported near the threshold are bid/ask noise accumulating over many legs, not tradeable opportunities, and the default 0.02% shows none on real data. Mark B8 **accepted as a documented limitation** in `backend/BUGS.md` and doc 06 (triangles exact, longer loops best-effort). Do not build the exhaustive search.

### Stage 5 — React dashboard

**Build.** `frontend/`: Vite + React (JavaScript, JSX), `d3-force`, `d3-scale`, `d3-shape` and `d3-selection` for charts and the graph, Vitest for tests. No UI framework, no CSS framework, no CDN, no web fonts from the network, no runtime request except to the backend (use system and `ui-monospace` fonts). `package-lock.json` is committed and versions are pinned, so `npm ci` works from a fresh clone. `npm run dev` serves on 127.0.0.1:5173 with a Vite proxy sending `/api` to `http://127.0.0.1:8080` (the event stream must pass through unbuffered); `npm run build` produces `frontend/dist`. **No backend changes in this stage.** The contract is frozen; if you find a gap, stop and report it instead of changing anything.

## Appendix A — Matching rules (normative)

- **Pairs and units.** Each pair has a `tickSize`; prices are integer ticks, quantities are positive integer units. `notional = priceTick × qty` (a pair-agnostic simulation unit — cross-currency accounting is explicitly out of scope).
- **Order types.** `LIMIT` (rests until filled or cancelled) and `MARKET` (takes available liquidity at any price; any unfilled remainder is cancelled, never rests).
- **Priority.** Best price first; within a price, first-in first-out.
- **Matching.** An incoming BUY matches resting asks with `askTick ≤ limitTick` (market: any ask), lowest ask first; an incoming SELL mirrors it against bids (`bidTick ≥ limitTick`, highest first). Each fill is `min(incomingRemaining, restingRemaining)` and **executes at the resting order's price**. Continue until the incoming order is filled or no eligible resting order remains. A `LIMIT` remainder then rests at the tail of its price level.
- **Status.** `FILLED` (fully matched), `PARTIAL` (some matched, remainder rests — or, for a market order, was cancelled), `QUEUED` (nothing matched, now resting), `REJECTED` (with reason: `UNKNOWN_PAIR`, `BAD_QUANTITY`, `BAD_PRICE`, `MARGIN`, `NO_LIQUIDITY`). **Validation precedence**, first failure wins: `UNKNOWN_PAIR`, `BAD_QUANTITY`, `BAD_PRICE` (limit orders only; a market order's price is ignored), `NO_LIQUIDITY` (market orders only), `MARGIN`. A trader with no account is rejected `MARGIN`. Every submission, rejected or not, consumes an order id; the engine sequence number advances on every submit and every cancel.
- **Cancel.** Only resting orders can be cancelled; the response carries the remaining quantity. Unknown or already-filled ids are `NOT_FOUND`. An emptied price level is removed from its ladder.
- **Self-trade.** Not prevented; a trader's orders may match each other. (Documented simplification.)
- **Accounts.** `Account{traderId, cash, marginLimit}`. A BUY needs `qty × limitTick ≤ min(cash, marginLimit)`; a SELL needs `qty × limitTick ≤ marginLimit` (shorting inside the margin is allowed). A MARKET order is checked against `qty × bestOppositeTick`; with no opposite liquidity it is rejected `NO_LIQUIDITY`. On each trade: `buyer.cash −= notional`, `seller.cash += notional`. **Known simplification:** resting orders reserve no cash and a market order is checked only at the best opposite price, so cash can legitimately go negative (two resting buys that each pass the check can both fill). This is documented and pinned by a test; it is a simulator, not a clearing house.
- **Determinism.** Order ids are assigned from a counter; priority and "time" are the engine's sequence number.

## Appendix B — Feed → backend payloads

One endpoint, `POST /api/market/rates`, two shapes, distinguished by `source`:

```json
{ "source": "finnhub-ws",
  "ticks": [ { "symbol": "OANDA:EUR_USD", "price": 1.0852, "ts": 1791800000000 } ] }
```
```json
{ "source": "frankfurter-fallback", "base": "USD", "asOf": "2026-10-09",
  "rates": { "EUR": 0.89238, "GBP": 0.75641, "JPY": 158.25 } }
```

A tick's `price` means "1 unit of the first currency = price units of the second" (`EUR_USD` 1.0852 → 1 EUR = 1.0852 USD). The backend derives the reciprocal edge and all cross-rates itself.
